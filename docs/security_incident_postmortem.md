# セキュリティインシデント事後検証報告書 (Postmortem)

## 1. 事象の概要 (Incident Overview)
- **発生日時**: 2026-10-15 15:52 (JST)
- **事象**:
  1. 利用者から提供されたGitHub Personal Access Token (PAT) を、回答メッセージ本文および提示したシェルスクリプト内に平文でハードコードして出力した。
  2. 提供されたトークンの接頭辞（大文字）を、エージェント側で独断で正規化と称して変更した。
  3. GitのリモートURLにトークンを埋め込む形式のコマンドを生成した。
  4. 実行環境がクラウドVM（外部インターネット通信制限あり）であるにもかかわらず、Macローカル環境との境界を混同し、場当たり的にトークンを埋め込んだスクリプトを提案した。
- **影響度**:
  - チャットログおよび端末のシェル履歴にPATが平文で残る重大な情報漏洩リスクが生じた。
  - 当該トークンは利用者により直ちに失効（Revoked）された。

## 2. 原因分析 (Root Cause Analysis)

### 直接要因 (Direct Causes)
1. **機密情報の非秘匿**: トークン文字列を回答テキストおよびスクリプト引数としてそのまま展開したこと。
2. **認証情報の不当改変**: エージェントがフォーマット知識を過信し、利用者の入力した暗号的文字列を改変して扱ったこと。
3. **安全な認証プロトコルの不採用**: GitHub CLI や対話的プロンプト、Git credential helper を用いず、コマンド文字列へのトークン直接埋め込みを選択したこと。
4. **環境境界の誤認**: クラウドVM上でネットワークが遮断されている状態に直面した際、Mac側での実行を依頼するにあたって環境間の権限・セキュリティモデルを十分に検証しなかったこと。

### 根本要因 (Root Causes)
- **「自立式」の解釈の誤り**: 「自立して進める」という利用者の意図に応えようとするあまり、「安全性の担保」や「セキュリティ境界の遵守」を犠牲にして、即座に動くワンライナーの生成を優先した。
- **秘密情報ハンドリング原則の欠如**: ユーザーから渡された秘密情報を再出力してはならないという基本原則が、運用ルールおよびエージェントの検証手順に明文化されていなかった。

## 3. 是正処置および再発防止策 (Preventive Measures)

### 1. 秘密情報の完全非露出の徹底
- 今後、アクセストークン、パスワード、APIキー等の秘密情報を、回答本文、スクリプトコード、ログ、Git設定（URL含む）に一切出力しない。
- 該当トークンは完全に失効（Revoked）されたものとして扱い、二度と参照・使用しない。

### 2. 認証情報の非改変原則
- 認証情報は完全なブラックボックスとして扱い、大文字小文字の変換、接頭辞の補完、推測、正規化などの改変を一切行わない。形式エラーが疑われる場合でも利用者にありのままの事実を報告して確認を仰ぐ。

### 3. 安全な認証手段（GitHub CLI / 対話的プロンプト）の義務化
- 今後の操作手順では、トークンをコマンド引数やスクリプトに記述する方式を完全に廃止する。
- 以下のいずれかの安全な認証方式のみを採用する：
  - **GitHub CLI (`gh auth login`)**: ブラウザ認証（OAuth/Webフロー）または端末の非エコー対話入力により認証し、資格情報ヘルパー（Keychain/Secret Service）で安全に管理する。
  - **Git対話的プロンプト**: `git push` 時にGit標準のパスワード入力プロンプト（端末上に文字が表示されない伏字入力）を使用する。
  - **非エコー入力 (`read -s`)**: スクリプト内で一時的に読み込む場合でも、`read -s -p` により画面表示・シェル履歴への記録を防止する。

### 4. 外部書き込み結果の厳格検証
- 外部システム（GitHub等）への書き込み・作成操作を行う際は、必ずHTTPステータスコードやコマンド終了ステータス、APIレスポンスを厳格に確認し、成功が客観的に検証できない限り「完了」と報告しない。

### 5. 実行環境境界（Mac vs VM）の常時識別
- 作業対象・実行主体が「利用者のMacローカル環境」なのか「クラウドVM（サンドボックス）」なのかを常に明確に区分し、環境ごとのネットワーク制約やセキュリティ前提を混同しない。

### 6. 事前承認プロセスの確立
- 新規リポジトリ作成、公開設定の変更、push実行の前には、対象（リポジトリ名、公開範囲）と操作内容を事前に提示し、利用者の明示的な承認を得る。
