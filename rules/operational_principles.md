# 運用・開発原則 (Operational Principles)

## 1. 自律的継続と問題記録
調査・開発の過程で不整合や問題を発見した場合は、以下の手順を踏み、原則として自律的に作業を継続する。
1. **原因と修正内容の記録**: 発生要因（Root Cause）と是正内容を明確にログ・コミットメッセージ・変更履歴に記録する。
2. **自動テストの実行**: 修正後に回帰テスト・整合性テストを実行し、品質を検証する。
3. **作業の継続**: 軽微なデータ不整合や形式修正については作業を止めずに前進させる。

## 2. 作業停止と確認を求める例外基準（キルスイッチ）
以下の重大な判断が必要な事象が発生した場合は、直ちに作業を停止し、こうじさんに確認・承認を求める。
- **原資料の同一性を損なう変更**: 一次資料と矛盾する値の強制上書き、または根拠不明な推測値の混入リスクがある場合。
- **データの消失リスク**: 既存の検証済みCanonical Dataや履歴ログが失われる恐れがある場合。
- **セキュリティ・権限上の問題**: トークン、認証情報、外部サービスへの意図しないアクセス権限付与等の懸念がある場合。

## 3. タイムスタンプの独立管理原則
- **ファイル生成日時 (`created_at` / ファイルシステムのタイムスタンプ)** と **原資料の検証日時 (`verified_at` / `accessed_date`)** は厳格に分離して管理する。
- ファイル生成日時から原資料の検証日時を逆算・推定・擬制することを固く禁止する。
- `verified_at` には、エージェントまたは人間が実際に原資料（Webページ、条例、要覧等）を閲覧・照合した実績日時のみを記録する。

## 4. セキュリティおよび外部連携原則 (Security & External Integration)
1. **秘密情報の完全非露出**: アクセストークン、APIキー、パスワード等の秘密情報を回答本文・ログ・コード・GitリモートURL・コミット履歴に出力しない。
2. **認証情報の改変禁止**: 認証情報を推測、補完、正規化、改変しない。提供された文字列をそのまま利用するか、形式不適合の場合は利用者に対応を依頼する。
3. **安全な認証手段の優先利用**: GitHub等の外部サービス操作には、可能な限りGitHub CLI（`gh auth login`）や資格情報ヘルパーなどの安全な認証手段を使用する。
4. **外部書き込み結果の厳格検証**: 外部システムへの書き込みでは、処理結果とエラーを確実に確認し、成功が確認できない場合は完了と報告しない。
5. **実行環境境界の厳格識別**: 実行環境が利用者のMacローカル環境なのかクラウドVMなのかを混同せず、各環境のネットワーク接続性やアクセス権限の差異を前提に手順を設計する。
6. **破壊的・対外操作前の承認必須**: 新規リポジトリ作成、公開設定、push等の外部公開を伴う操作の前には、対象と内容について必ず利用者の承認を得る。
